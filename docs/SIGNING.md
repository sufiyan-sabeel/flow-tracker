# Signing Flow-tracker releases

New to this? Start with **[SIGNING-SETUP.md](SIGNING-SETUP.md)** — it walks through
obtaining each certificate, exporting it, and adding the secrets, in order. This
file is the reference: what each secret is and what the pipeline verifies.


The release pipeline signs every artifact with a production identity and verifies
the signature with the platform's own tool. There is no unsigned path and no
debug-key fallback: if a credential is missing, `preflight` fails in about a
minute and names what is missing, before any platform is built.

Everything below is a value you create and keep. Nothing here is generated by the
pipeline, and no private key is ever written into the repository.

## Secrets to add

Add these under **Settings → Secrets and variables → Actions**, in an environment
named `release` (every signing job declares `environment: release`, so you can
require manual approval and restrict who may run it).

### Android

| Secret | What it is |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | your release `.jks`, base64 encoded |
| `ANDROID_KEYSTORE_PASSWORD` | keystore password |
| `ANDROID_KEY_ALIAS` | key alias inside the keystore |
| `ANDROID_KEY_PASSWORD` | key password |

Create one keystore, once, and keep it safe — this identity must stay the same
for every future release or Android will refuse to install the update:

```bash
keytool -genkeypair -v -keystore flow-tracker-release.jks \
  -keyalg RSA -keysize 4096 -validity 10000 \
  -alias flow-tracker -storetype JKS
base64 -w0 flow-tracker-release.jks    # paste into ANDROID_KEYSTORE_BASE64
```

Back the `.jks` up somewhere durable. Losing it means you can never update the
published app again under the same identity.

### iOS

| Secret | What it is |
| --- | --- |
| `IOS_CERT_P12_BASE64` | Apple **Distribution** certificate + private key, exported as `.p12` |
| `IOS_CERT_PASSWORD` | password set on that `.p12` |
| `IOS_PROVISION_PROFILE_BASE64` | App Store provisioning profile for `com.flowtracker.app` |
| `IOS_TEAM_ID` | your Apple Developer team id |

From the Apple Developer portal: create an Apple Distribution certificate, an App
Store provisioning profile for `com.flowtracker.app`, download both, then:

```bash
base64 -w0 distribution.p12                    # IOS_CERT_P12_BASE64
base64 -w0 FlowTracker_AppStore.mobileprovision # IOS_PROVISION_PROFILE_BASE64
```

The build exports with `method=app-store-connect`, `signingStyle=manual`, so the
profile must be an App Store profile for that exact bundle id.

### Windows

| Secret | What it is |
| --- | --- |
| `WINDOWS_PFX_BASE64` | Authenticode code-signing certificate + private key, `.pfx` |
| `WINDOWS_PFX_PASSWORD` | password on the `.pfx` |

Buy an OV or EV code-signing certificate from a CA (DigiCert, Sectigo, SSL.com
and others). Export it as `.pfx` including the private key, then:

```bash
base64 -w0 codesign.pfx     # WINDOWS_PFX_BASE64
```

The pipeline signs with SHA-256 and an RFC 3161 timestamp, then verifies with
`signtool verify /pa /all` and checks that the signer subject contains the
publisher name and that a timestamp is present.

SmartScreen reputation is **not** something a signature guarantees. A new
certificate starts with no reputation; warnings fade as downloads accumulate. EV
certificates historically build reputation faster, but neither is instant.

### Linux (GPG)

| Secret | What it is |
| --- | --- |
| `GPG_PRIVATE_KEY_BASE64` | your signing key, exported and base64 encoded |
| `GPG_PASSPHRASE` | passphrase on that key |
| `GPG_KEY_ID` | key id or full fingerprint |

```bash
gpg --full-generate-key          # RSA 4096, no expiry, real identity
gpg --armor --export-secret-keys <KEY_ID> | base64 -w0   # GPG_PRIVATE_KEY_BASE64
gpg --fingerprint <KEY_ID>       # the fingerprint goes in GPG_KEY_ID
```

Publish the fingerprint in your README so users can confirm the key they import
is the key you use. The pipeline attaches the public key as
`flow-tracker-signing-key.asc` and produces a detached `.asc` for the DEB and for
the AppImage.

### macOS

| Secret | What it is |
| --- | --- |
| `MACOS_CERT_P12_BASE64` | **Developer ID Application** certificate + key (`.p12`) |
| `MACOS_CERT_PASSWORD` | its password |
| `MACOS_INSTALLER_P12_BASE64` | **Developer ID Installer** certificate + key (`.p12`) |
| `MACOS_INSTALLER_PASSWORD` | its password |
| `MACOS_TEAM_ID` | your team id |
| `MACOS_NOTARY_APPLE_ID` | the Apple ID used for notarization |
| `MACOS_NOTARY_PASSWORD` | an app-specific password for that Apple ID |

Two certificates are needed: one signs the `.app` and the `.dmg`, the other signs
the `.pkg`. Notarization uses `notarytool`; the pipeline waits for the result,
staples the ticket and then checks `spctl --assess` for both the app and the
installer.

## What the pipeline does with them

1. **preflight** — verifies the tag matches `pubspec.yaml` and `RELEASE_TAG`,
   checks all twenty secrets are non-empty, fails with the list of missing ones,
   runs formatting, analysis and the full test suite, and reads the Android
   certificate SHA-256 so later steps can prove the APK was signed by it.
2. **android** — builds with the keystore, then `apksigner verify --print-certs`
   (v2 scheme, not the debug key, fingerprint match) and
   `jarsigner -verify -strict` on the AAB.
3. **ios** — imports the certificate into a temporary keychain, installs the
   profile, exports a signed IPA, then `codesign --verify --deep --strict`,
   checks the authority is `Apple Distribution`, checks the team identifier, and
   inspects the embedded profile.
4. **windows** — builds the EXE and MSI, signs both with `signtool`, then
   `signtool verify /pa /all`, checks `Get-AuthenticodeSignature` status is
   `Valid`, the subject contains the publisher, and a timestamp exists.
5. **linux** — builds the DEB and AppImage, signs each with a detached GPG
   signature, verifies both, and exports the public key.
6. **macos** — signs frameworks and the app inside-out with hardened runtime,
   signs the PKG with the installer identity, signs the DMG, notarizes both,
   staples, then verifies with `codesign`, `pkgutil --check-signature`,
   `spctl --assess` and `hdiutil verify`.
7. **publish** — only runs when all five platform jobs succeeded. It attaches the
   verified artifacts, the `.asc` signatures, the public key and
   `SHA256SUMS.txt`, and its notes carry the signing status per platform.


## Two modes: signed and explicitly unsigned

The workflow has a `signing` input with two values.

- **`required`** (default, and the only mode a tag push can use) — every
  credential must be present, every artifact is signed, every signature is
  verified. If a credential is missing the run stops at preflight and nothing is
  built.
- **`unsigned`** — a manual dispatch only. It builds the same five platforms and
  publishes them, but the release notes open with an **UNSIGNED BUILD — NOT A
  PRODUCTION RELEASE** banner, the signing table says "Unsigned" per platform,
  and the iOS artifact is named `-iOS-unsigned.ipa`. Nothing in this mode is
  described as signed.

An unsigned build is never produced by accident: it requires choosing it in the
dispatch form, and a tag push cannot select it.

## Verifying a download yourself

```bash
sha256sum -c SHA256SUMS.txt
gpg --import flow-tracker-signing-key.asc
gpg --verify Flow-Tracker-<version>-Linux-amd64.deb.asc \
             Flow-Tracker-<version>-Linux-amd64.deb
```

The AppImage has its own `.asc`; it is a separate signature over a separate file,
not the DEB's signature reused.

## If a credential is wrong

The run fails at the step that verifies it, with the tool's own output — a
`codesign` error, a `signtool` error, a `gpg` error. The pipeline never retries
without signing and never publishes a partially signed set.
